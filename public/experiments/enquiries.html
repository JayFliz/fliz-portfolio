Enquiries Module — Scope & Design

June 2026 · Draft · Engineering · Ceroc Admin Platform

1. Overview

The Enquiries module captures inbound interest from potential and existing dancers — typically via the public website — and routes them to the correct franchise for follow-up. An admin reviews enquiries, optionally triggers a welcome email via Iterable, and can convert an enquiry into a member record.

The backend API is shared between this admin app and the public website (at minimum). The admin UI is a module within this project following existing patterns.

System Flow

Public Website

  • Dancer fills in enquiry form
  • Name, email, phone, postcode
  • Optional: venue or offer link
  • Free-text message
➔

BookingZapp API

  • Receives POST /enquiries
  • Resolves territory from postcode / venue / offer
  • Sets status: New
  • Stores enquiry for admin review
➔

Admin App

  • Admin reviews in Enquiries list
  • Sets type, status, follow-up flag
  • Triggers Iterable email
  • Converts to member (optional)

Territory Routing Logic

InputResolution
PostcodeLook up TerritoryPostcodeAllocation to find the owning territory
Venue IDVenue record has a territoryID — use directly
Offer IDOffer belongs to an event which belongs to a territory
NoneAssign to unrouted queue for manual triage

5. Iterable Integration

Architecture

Admin App

Admin clicks
"Send Welcome Email"

➔

BookingZapp API

Resolves venue, class dates,
territory contact info

➔

Iterable

Sends templated email
to the enquirer

  • Admin-triggered only — no auto-send on website submission. Admin reviews first.
  • Template selection — admin picks from configured Iterable templates via a modal dialog.
  • Data resolution is server-side — the API resolves nearest venue, next class dates, and territory contact details before calling Iterable.
  • Audit trail — iterableMessageID stored on the enquiry for tracking.
  • Iterable API key and template IDs are backend config — never exposed to the frontend.
