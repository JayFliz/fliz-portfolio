01 Discover an Event
Dancer hears about a Ceroc event: sees it on the website, receives an Iterable email, follows a social media post, or hears through word of mouth.
Data presented
  • Event name, date, time
  • Venue name and location
  • Starting price / "from £X"
  • Event images and description
  • Territory / area name
Data captured
  • Page view (analytics)
  • Email open / click (if Iterable)
  • UTM parameters (campaign source)
Website Iterable API
Discount — Promotional codes shared in email campaigns or social posts
02 Browse & Choose
Dancer browses events by location and date. Views event details, entry types, pricing tiers, and available offers. Decides which event to attend.
Data presented
  • Events list filtered by location/date/territory
  • Distance from dancer (if location shared)
  • Entry types with per-tier pricing
  • Available offers (bundles, packages)
  • Capacity / sold-out status
  • Venue details (address, rooms, facilities)
Data captured
  • Search filters applied
  • Events viewed (engagement tracking)
  • Favourited events / offers
Member App Website API
03 Sign In or Create Account
To book, the dancer must authenticate. Existing members sign in. New members discover their record via "Find Me" (matched by name, DOB, email) or register fresh. OTP verification confirms identity.
Data presented
  • Sign-in form (email + password)
  • Find Me search (name, DOB, email, phone, postcode)
  • Matched member records (scored)
  • OTP input screen
  • Registration form (if no record found)
Data captured
  • Login credentials (email, password)
  • OTP verification result
  • New member: name, DOB, gender, email, phone, address
  • Member-to-record match (duplicate merge)
  • OAuth2 access token issued
SSO API
Two paths to the event
Pre-booked path
4A Book & Pay Online
Dancer selects entry type or offer, applies a discount code if they have one, enters payment details, and confirms the booking.
Data presented
  • Entry types with prices
  • Available offers (bundles)
  • Discount code input field
  • Cart summary + total
  • Loyalty status: "You'll earn a stamp"
  • Stripe payment form
Data captured
  • Selected entry type / offer
  • Discount code (validated)
  • Stripe payment intent + charge ID
  • Booking record created (status: Confirmed)
  • Transaction record with amount
Member App API
Discount — Code applied at checkout, validated against territory scope and usage limits
Loyalty — Stamp preview shown; stamp awarded after attendance confirmed
Payment — Stripe checkout: card payment, receipt generated, payment state stored on booking
5A Receive Confirmation
Booking confirmed on screen and by email. Includes QR code for check-in, event details, and receipt.
Data presented
  • Booking confirmation screen
  • Email: event details, venue address, QR code
  • Payment receipt (amount, method)
  • Cancellation policy
Data captured
  • Confirmation email sent timestamp
  • Email open tracking
  • QR code generated (booking ref encoded)
Iterable Member App
6A Get Reminder
24 hours before the event: email and/or push notification with venue directions and a reminder to attend.
Data presented
  • Event name, time, venue
  • Directions / map link
  • "See you tomorrow" messaging
Data captured
  • Reminder sent timestamp
  • Open / click tracking
  • Push notification delivered
Iterable
Walk-in path
4B Just Turn Up
Dancer arrives at the venue without a booking. This is the current primary path for most Ceroc events — no pre-booking, no payment in advance.
Data presented
  • N/A (dancer arrives physically)
Data captured
  • N/A (no digital touchpoint until check-in)
5B–6B No Confirmation / Reminder
Walk-ins receive no pre-event communication. After their first attendance, they enter the welcome series (if email is captured at the door).
Both paths converge at the door
07 Check In at the Door
Door staff find the dancer by QR scan or name search. Pre-booked members: booking matched, entry type pre-selected, payment status shown as pre-paid. Walk-ins: entry type selected, payment taken at door (cash or card).
Data presented to door staff
  • Member name, photo, card number
  • Booking status (Confirmed / Pre-paid / Walk-in)
  • Entry type (pre-selected for bookings)
  • Member completeness check (email verified?)
  • Age check (under-16 alert)
  • Entry fee exemptions (EFE status, uses remaining)
  • Crew role (if assigned to event)
  • Loyalty stamp count and programme status
Data captured
  • Attendance record (member + event + entry type)
  • Payment method (pre-paid / cash / card at door)
  • Check-in timestamp
  • Booking status update: Confirmed → Attended
  • Email verification (door staff confirms accuracy)
  • New member creation (if first-time walk-in)
Venue App API
Loyalty — Stamp awarded on check-in (auto or manual). Milestone reached? Reward unlocked.
Discount — EFE (entry fee exemption) applied if valid. Promotional entry validated.
Payment — Walk-in: cash/card at door. Pre-booked: "Pre-paid" badge, no payment needed.
08 Attend the Event
Dancer participates in the event: beginner lesson, freestyle, social dancing. This is the core product — everything else exists to get people here and bring them back.
Data presented (event dashboard)
  • Live attendance count vs capacity
  • Gender breakdown
  • Booking vs walk-in ratio
  • Revenue to-date (pre-paid + door)
Data captured
  • Running attendance totals
  • Event expenses (DJ, venue hire, supplies)
  • Crew attendance and roles
Venue App
09 Post-Event Follow-Up
After the event: door staff mark it as "Reporting" status. Iterable sends a follow-up email. First-time attendees get the welcome series. Loyalty stamp confirmation sent.
Data presented (to dancer)
  • "Thanks for coming" email
  • Next local events (book your next one)
  • Loyalty update: "You earned a stamp! X more until reward"
  • First-timers: "Set up your account" welcome series
Data captured
  • Event status → Reporting
  • Attendance event fired to Iterable
  • Email open / click tracking
  • Welcome series engagement
Venue App Iterable API
Loyalty — Stamp confirmation. Milestone messaging: "2 more stamps until free entry!"
10 Complete, Invoice & Report
HQ generates invoices from service charges on attendance. Payment recorded. Franchisee dashboard shows territory KPIs. This step is invisible to the dancer but closes the business loop.
Data presented (to HQ / franchisee)
  • Invoice: service charges calculated from attendance × rates
  • Revenue breakdown: pre-paid vs door payments
  • Expense summary (from venue app)
  • Franchisee dashboard: attendance trends, member growth, fill rates
  • Booking conversion: how many bookings became attendances
Data captured
  • Invoice record (Draft → Issued → Paid)
  • Payment received timestamp and amount
  • Service charge line items
  • Discount code usage report (codes used, revenue impact)
  • Loyalty programme report (stamps issued, rewards redeemed)
Admin App API
Discount — Usage report: which codes were redeemed, revenue impact, territory breakdown
Loyalty — Programme report: stamps issued this period, rewards redeemed, active cards
Payment — Reconciliation: Stripe payouts vs door cash vs invoice charges
11 Return & Grow
The dancer returns. They book their next event, earn more loyalty stamps, redeem rewards, and receive targeted communications based on their attendance history and territory. Lapsed dancers get win-back campaigns. The cycle repeats from step 2.
Data presented
  • Upcoming events near them
  • Loyalty card progress (stamps, next reward)
  • Available rewards to redeem
  • Personalised offers based on attendance history
  • Targeted discount codes (Iterable segments)
  • Win-back emails (30/60/90 day lapse)
Data captured
  • Attendance frequency and recency
  • Churn risk score (days since last attendance)
  • Loyalty: stamps earned, rewards redeemed
  • Discount: targeted codes issued, redemption rate
  • Iterable engagement: email opens, click-throughs
  • Lifetime value: total events attended, total spend
Member App Iterable API
Loyalty — Full programme: card display, stamp progress, reward catalogue, redemption at door or online
Discount — Targeted codes: segment-based (lapsed dancers, VIPs, new members), territory-scoped
